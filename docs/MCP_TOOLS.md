# Dreamwork MCP Tools Reference

## Overview

Dreamwork exposes an MCP tool catalog that lets AI agents operate a person's job search: browsing listings, saving roles, tailoring materials, applying, and tracking what came back. The MCP server calls the Dreamwork API over HTTP using the same per-person auth and access rules as the product.

**API origin:** `https://api.dreamworkhq.com`

**MCP package:** `npx -y @dreamworkhq/mcp` in stdio mode.

**Hosted endpoint:** `https://mcp.dreamworkhq.com/mcp` over Streamable HTTP. claude.ai, Claude Desktop, and ChatGPT connectors sign in with OAuth; clients that set headers can send an agent key as a bearer. `docs/MCP_HOSTED.md` has the details.

**Auth:** The stdio package takes a Dreamwork agent key that starts with `sk_`, passed as `DREAMWORK_API_KEY` in the MCP client config.

**Key scopes:** a key carries a subset of `read`, `write`, `apply`, and `send`, chosen when you generate it in Dreamwork.

`apply` and `send` gate every path, not just the MCP tools. A key without `apply` cannot submit an application, cancel one that is still sending, or change Autopilot. Not through `apply` or `apply_to_job`, not through `POST /assistant/actions/apply`, and not by calling `POST /jobs/:id/apply`, the turbo-apply routes, or the escalation routes over plain HTTP. A key without `send` cannot mail a recruiter through `reply_to_recruiter`, `send_outreach`, `POST /outreach/send`, or `POST /conversations/:id/reply`. Direct HTTP calls to those routes answer 403 `{"error":"api_key_scope_required","scope":"apply"}` before the handler runs; assistant actions answer `action_not_authorized` with a next step naming the scope.

`write` is the floor for changing anything at all. A key without it is refused on every request that is not a `GET`, `HEAD`, or `OPTIONS`, so a `read` key cannot rewrite a profile, generate a pack, or move the board by any path. The two exceptions are `POST /assistant/actions/:id` and `POST /assistant/turns`, which price each action individually and refuse the write ones on their own.

New keys default to read and write, so a key generated without a decision cannot submit or send. Keys created before scopes existed keep everything they could already do; nothing is taken away by the upgrade.

Key lifecycle is session-only: a key cannot read, create, or revoke keys, rotate the session token, or delete the account. Nor can it upgrade a subscription to Dreamer at list price (`POST /billing/upgrade-to-dreamer`), which charges the card on file immediately. Those answer 403 `{"error":"session_required"}`.

**Confirming an irreversible act:** the five consequential actions (`apply`, `set_autopilot`, `update_autopilot_settings`, `reply_to_recruiter`, `start_checkout`) do not run on their first call. They answer `held` with a summary of exactly what would happen and a `confirmationToken`. Show the summary to the person; if they agree, call the same tool again with identical arguments plus that token. A changed argument is held again with a fresh token and a fresh summary, so a "yes" can only ever authorize the act that was described. The token lasts two minutes and is spent once.

One tool per capability in the assistant registry (`packages/assistant-contracts`), each called through `POST /assistant/actions/<id>`. ## Application Workflow

`apply` is the current path. It asks first:

```
apply(applicationId, expectedRevision)
  -> held: a summary of the role and the materials, plus a confirmationToken
apply(applicationId, expectedRevision, confirmationToken)
  -> POST /jobs/:id/apply
  -> Dreamwork checks role fit, candidate readiness, and application state
  -> fences the send against the materials revision that was read
  -> Submits when the workflow is eligible, or returns candidate-review state
  -> a receipt, usually `queued`, with a cancel the agent can call
```

`apply_to_job`, the older tool that submitted on its first call, was removed in 1.3.0.

The web app and MCP tools share the same backend application state. When Dreamwork needs more context or candidate approval, the workflow returns a review state instead of silently proceeding.

## Getting an API Key

The MCP server needs a Dreamwork agent key to authenticate as your account.

**Create an agent key:**

1. Log into Dreamwork at `https://www.dreamworkhq.com`
2. Open Settings or the agent access drawer
3. Tick what the key may do, then generate it
4. Copy the `sk_...` key once and store it in your MCP client configuration

The key is scoped to your candidate account, carries the scopes you picked, and is subject to rate limits. A key's scopes are fixed when it is made: to change them, revoke it and generate another. Do not expose it in browser code or public repositories.

## Testing The MCP Workflow

### Prerequisites
- An active Dreamwork account
- A profile with resume context
- A job in your pipeline with an application URL, or a listing you can add to the pipeline
- A Dreamwork agent key that starts with `sk_`

### Via Claude Desktop / Cursor / Warp MCP

Configure the MCP server:

```json
{
  "mcpServers": {
    "dreamwork": {
      "command": "npx",
      "args": ["-y", "@dreamworkhq/mcp"],
      "env": {
        "DREAMWORK_API_KEY": "sk_...",
        "DREAMWORK_API_URL": "https://api.dreamworkhq.com"
      }
    }
  }
}
```

Then ask the agent:

1. "Browse listings for Stripe" calls `browse_listings`
2. "Add that first listing to my pipeline" calls `save_job`
3. "Apply to that job" calls `apply`, which comes back held with a summary; say yes and the agent calls it again with the token

Watch the tool result and Dreamwork pipeline state for the saved job, generated materials, review state, or submission status.

### Via curl (direct API)

```bash
# 1. Find a job in your pipeline
curl -H "Authorization: Bearer $DREAMWORK_API_KEY" \
  https://api.dreamworkhq.com/jobs?limit=5

# 2. Trigger apply (replace JOB_ID)
curl -X POST -H "Authorization: Bearer $DREAMWORK_API_KEY" \
  https://api.dreamworkhq.com/jobs/JOB_ID/apply
```

### Expected Result

`apply_to_job` returns updated application state. Depending on the candidate profile, job data, and application requirements, that state may be submitted, pack-ready, in progress, or waiting for candidate review.

### Troubleshooting

- **"No application URL available"** - The job has no `url` field. Import it from a URL or add one manually.
- **"Profile not found"** - Complete your Dreamwork profile and add resume context before applying.
- **Review state returned** - Dreamwork needs candidate input before it can proceed. Resolve the review item in Dreamwork, then retry.
- **Timeout** - Some application workflows take longer or require human review. Check the saved job status before retrying.
- **"AI decided not to apply"** - The role did not pass the current readiness or fit checks. Review the job details and candidate preferences.
